Accessibility Is Context

Permanent

Blindness, low vision, deafness, motor disability, cognitive disability.

Temporary

Broken arm, eye strain, migraine, lost headphones, slow connection.

Situational

Bright sunlight, noisy train, one-handed use, old device, limited time.

Accessible work is not extra polish. It is resilient design.

The POUR Model

P O U R

POUR is the mental shortcut for WCAG's four accessibility principles.

What POUR Stands For

Perceivable Operable Understandable Robust

Use these words as audit questions: can people get the information, operate the interface, understand the result, and rely on the code with assistive technology?

POUR

Perceivable: Can People Get the Information?

Content alternatives

Images need useful alt decisions, video needs captions, audio needs transcripts when speech matters.

Visual access

Text contrast, readable sizing, and not relying on color alone all live here.

Adaptable content

The same content should still make sense when zoomed, read aloud, simplified, or rearranged.

POUR

Operable: Can People Use the Interface?

Keyboard access

Every interactive thing needs a keyboard path, not only mouse, hover, drag, or touch.

Visible focus

Users need to know where they are before they can decide what to do next.

Safe interaction

Avoid traps, surprise movement, tiny targets, and interactions that demand precision.

POUR

Understandable: Can People Predict What Happens?

Clear language

Labels, headings, links, and errors should describe purpose instead of making users guess.

Consistent patterns

Navigation, repeated components, and help should appear and behave consistently.

Helpful recovery

Forms should explain what went wrong, where it happened, and how to fix it.

POUR

Robust: Can Tools Understand the Page?

Valid semantics

Use the right HTML element so browsers, screen readers, and future tools receive the same meaning.

Names and states

Controls need programmatic names, roles, values, and states when native HTML is not enough.

Progressive enhancement

Build the core experience in resilient HTML before adding styling and JavaScript behavior.

Manual Audit Flow

Keyboard Focus Structure Names Contrast Forms Motion Zoom

Automated tools help, but they do not understand intent. Human testing is part of the job.

Before You Start: Set Up the Audit

Pick the journey

Choose one realistic user task: browse, sign up, search, buy, contact, or submit.

Define the page state

Include menus, modals, errors, hover/focus states, and loaded content.

Record evidence

Write what happened, where, who it blocks, and the smallest useful fix.

Audit Step 1: Keyboard and Focus

Question

Can I complete the task without a mouse?

Check

Tab order, skipped controls, trapped focus, Escape behavior, visible focus, hidden sticky-header landings.

Evidence

"Newsletter close button cannot be reached with Tab" is better than "keyboard is bad".

Audit Step 2: Structure and Names

Question

Can the page be understood from headings, landmarks, links, buttons, image names, and form labels?

Check

One useful <h1>, heading order, landmark names, link purpose, icon buttons, alt decisions, input labels.

Evidence

"Three links are named Choose, so screen reader users cannot tell which plan each link selects."

Audit Step 3: Visual Access and Reflow

Question

Can people still read and use the page when the visual conditions change?

Check

Contrast, color-only meaning, 200% zoom, narrow viewport, text spacing, target size, reduced motion.

Evidence

"At 200% zoom the pricing cards require horizontal scrolling to read normal text."

Audit Step 4: Forms and Error Recovery

Question

Can users understand each field, enter the right data, and recover from mistakes?

Check

Labels, groups, required indicators, autocomplete, hints, error text, aria-describedby, aria-invalid.

Evidence

"The email error is visual only and is not connected to the email field."

Audit Notes Should Be Actionable

Weak noteBetter noteWhy it helps
"Bad accessibility.""The cart icon button has no accessible name."Names the issue and location.
"Contrast problem.""The muted nav links are 2.3:1 against the dark header."Gives measurable evidence.
"Keyboard broken.""The custom filter chip is skipped by Tab and cannot be toggled with Space."Explains user impact and expected behavior.

Focus Must Be Visible

Broken

*:focus {
  outline: none;
}

No visible position for keyboard users.

Better

:focus-visible {
  outline: 4px solid #e86f51;
  outline-offset: 4px;
}

Clear focus without showing rings for every mouse click.

:focus vs. :focus-visible

:focus

Matches whenever an element has focus: keyboard, mouse click, script focus, or touch depending on the browser.

button:focus {
  outline: 3px solid #2d5f9a;
}

:focus-visible

Matches when the browser decides a visible indicator is needed, especially keyboard navigation.

button:focus-visible {
  outline: 4px solid #e86f51;
  outline-offset: 4px;
}

Teach both: keep focus styles available, then use :focus-visible to make keyboard focus clear without noisy mouse-click rings.

Focus Must Not Be Covered

:target,
:focus-visible {
  scroll-margin-block: 6rem;
}

.skip-link:focus-visible {
  position: fixed;
  inset-block-start: 1rem;
  inset-inline-start: 1rem;
}

Sticky nav, cookie banners, and fixed toolbars can hide the focused thing. Leave room for focus to land.

Covered Focus Example

Sticky header Focused link hidden underneath Focused link with scroll margin 
main :focus-visible {
  outline: 4px solid #e86f51;
  outline-offset: 4px;
  scroll-margin-block-start: 5rem;
}

Heading Rules

<h1>Main page or view title. <h2>Major page sections. <h3>Subsections inside an <h2>. Do notChoose headings only because of visual size. DoStyle headings with CSS after the structure is correct.

Image Alt Text Decisions

InformativeDescribe the information the image contributes. FunctionalDescribe the action, such as "Search" or "Download report". DecorativeUse empty alt: alt="". ComplexSummarize nearby and link to full data if needed. Do notStart with "image of" unless the medium matters.

Color and Contrast

Pass

Text has enough contrast against its background.

Fail

Pretty is not enough if people cannot read it.

Do not communicate state with color alone. Pair color with text, icons, shape, or position.

Zoom and Reflow

Reflow means the layout rearranges into one readable direction instead of forcing people to scroll both sideways and vertically.

200%

Text should remain usable when browser zoom increases.

320 CSS px

Layouts should reflow without requiring two-dimensional scrolling for normal content.

rem

Use relative sizing for type and spacing that should respond to user settings.

clamp()

Set type and spacing ranges without locking the page to one viewport.

Forms Need More Than Labels

<label for="email">Email address</label>
<input
  id="email"
  name="email"
  type="email"
  autocomplete="email"
  required
  aria-describedby="email-hint"
/>
<p id="email-hint">Use the address for your course account.</p>

Error Messages

<label for="password">Password</label>
<input
  id="password"
  name="password"
  type="password"
  aria-invalid="true"
  aria-describedby="password-error"
/>
<p id="password-error">Password must be at least 12 characters.</p>

Tell users what happened, where it happened, and how to fix it.

Motion and Animation

@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms;
    animation-iteration-count: 1;
    scroll-behavior: auto;
  }
}

Keep animation purposeful, interruptible, and respectful of user preferences.

Pointer and Touch Targets

Size

Buttons and links need enough area for fingers, tremors, and rushed use.

Spacing

Small targets need extra distance from neighboring actions.

Alternatives

Do not require dragging when a button, field, or menu can do the same job.

Hover

Hover can enhance, but it cannot be the only way to reveal content.

Native Interaction Patterns

<button>Use for actions. It already supports keyboard activation. <a>Use for navigation to another URL or fragment. <details>Use for simple disclosure without custom JavaScript. <dialog>Use for modal tasks that temporarily take focus. popoverUse for non-modal teaching bubbles, menus, and small overlays.

ARIA Rules

Use native HTML first.

Do not change semantics unless you understand the keyboard pattern too.

ARIA can name and describe. It does not add behavior by itself.

No ARIA is better than wrong ARIA.

Important ARIA: Names and Descriptions

AttributeUse whenExample
aria-labelThere is no visible text to use as the name.<button aria-label="Close dialog">
aria-labelledbyVisible text elsewhere should name the control or region.<nav aria-labelledby="main-nav-title">
aria-describedbyHints, requirements, or errors should be announced with a field.<input aria-describedby="email-error">

Important ARIA: States and Relationships

aria-expanded

Disclosure, menu, or accordion button is open or closed.

aria-controls

Button controls another element, such as a menu panel.

aria-current

Current page, step, location, date, or item in a set.

aria-invalid

Form value failed validation and needs correction.

aria-live

Status updates should be announced without moving focus.

aria-hidden

Decorative or duplicate content should be ignored by assistive tech.

ARIA Does Not Add Behavior

Still broken

<div role="button" aria-pressed="false">
  Play
</div>

No built-in keyboard behavior, disabled behavior, or form behavior.

Better

<button type="button" aria-pressed="false">
  Play
</button>

Native role, keyboard support, focus behavior, and state can work together.
